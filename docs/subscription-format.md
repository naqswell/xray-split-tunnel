# Формат подписки

## Поддерживаемый вход

Установщик принимает JSON, из которого можно получить один или несколько
полных конфигов xray-core. Каждый пригодный элемент обязан быть JSON-объектом с
непустым массивом `outbounds`.

Поддерживаются четыре формы ответа:

1. массив полных конфигов;
2. один полный конфиг с корневым ключом `outbounds`;
3. объект-обёртка, где массив конфигов лежит в первом найденном ключе
   `configs`, `servers`, `items`, `data` или `subscription`;
4. локальный JSON-файл того же формата, переданный через `XST_SUB_FILE`.

Из массива сохраняются только объекты с `outbounds`. Если подходящих объектов
нет, нормализация завершается с ошибкой. Выбранный входной container может
содержать не более 512 candidate elements до фильтрации; превышение не
обрезается молча, а отклоняет всю подписку. Поэтому нормализованных config
тоже может быть только от 1 до 512. Это DoS guard в дополнение к лимиту
исходного JSON 10 MiB.

Первый outbound должен быть клиентским прокси, поддерживаемым Xray:
`hysteria`, `http`, `shadowsocks`, `socks`, `trojan`, `vless`, `vmess` или
`wireguard`. Служебные `freedom`, `blackhole`, `dns` и `loopback` не могут быть
основным VPN-outbound. Остальные provider outbounds сохраняются только для
тех же proxy protocols. Provider direct/DNS/control outbounds отбрасываются;
если proxy chain ссылался на такой detour, обязательный `xray run -test`
должен отклонить итог. Единственные `direct`/`block` создаются проектом.

Структурный пример без рабочих ключей:

```json
[
  {
    "remarks": "Основной сервер",
    "outbounds": [
      {
        "tag": "proxy",
        "protocol": "vless",
        "settings": {
          "vnext": []
        }
      }
    ]
  }
]
```

Этот фрагмент показывает только контейнер и не является рабочим VPN-конфигом.

## Что не поддерживается

- base64-строка со списком URI;
- отдельные `vless://`, `vmess://`, `trojan://` или `ss://` ссылки;
- Clash YAML;
- sing-box JSON, если в нём нет xray-совместимого `outbounds`;
- HTML-страница личного кабинета вместо JSON.

Такие данные сначала нужно конвертировать вне проекта в полный XRay JSON,
проверить локально и передать установщику как защищённый локальный файл.
Автоматически угадывать или преобразовывать неизвестный формат нельзя.

## Что меняется при применении

Выбранный конфиг копируется, после чего проект:

- полностью заменяет provider inbounds двумя контролируемыми HTTP/SOCKS
  listener на `127.0.0.1`;
- резервирует безопасные `direct` (`freedom`) и `block` (`blackhole`), не
  доверяя одноимённым тегам из подписки;
- сначала ставит правила явно перечисленных корпоративных доменов в `direct`;
- затем ставит правила приватных и дополнительных CIDR в `direct`;
- сохраняет proxy outbounds и только provider rules, ведущие в
  контролируемый `block`;
- отбрасывает provider DNS, API, metrics, stats, reverse, log paths и прочие
  top-level возможности, не нужные клиентскому VLESS/Reality-соединению.

Каждый config подписки обязательно проходит `xray run -test` до записи
состояния, чтобы последующий `xst switch` не активировал непроверенный вариант.
Подробный порядок маршрутизации описан в `how-it-works.md`.

При `xst update` индекс не является идентичностью сервера. Для текущего
элемента требуется явное непустое значение одного из полей `remarks`,
`remark`, `name`, `ps` или `tag`; полное необрезанное нормализованное имя
должно иметь единственное case-insensitive exact совпадение в новой подписке.
Внутри используется SHA-256 identity, а отображение может быть сокращено.
Числовое remarks, включая `0`, трактуется как имя, а не индекс. Если имя отсутствует,
удалено или дублируется, старые subscription/config/index остаются активными,
а оператор выбирает сервер вручную через `xst list`/`xst switch`.

Доменные значения нормализуются до suffix без схемы, пути, wildcard и
завершающей точки. CIDR канонизируются и дедуплицируются; default routes
`0.0.0.0/0` и `::/0` запрещены. Ошибка в любом значении не должна заменять
последний рабочий конфиг.

## Безопасная загрузка

Subscription URL — bearer-секрет. Его нельзя передавать в аргументе,
environment, чате или логе. При agent-driven установке Claude сам запускает
`scripts/capture-sub-url.sh`: пользователь вставляет URL в скрытый системный
диалог, helper безопасно создаёт `sub-url`, затем агент запускает установщик
без значения URL.

Сетевая загрузка разрешена только по HTTPS; переход на небезопасную схему
считается ошибкой. Cookie jar создаётся как временный файл и удаляется после
запроса.

Ответ провайдера и нормализованный JSON тоже секретны: в них могут быть UUID,
Reality public key, SNI и адрес сервера. Рабочие копии для импорта храните в
отдельном защищённом каталоге вне `XST_HOME`; managed state допускает только
файлы из своего строгого allowlist.

Для локального файла используйте отдельный защищённый каталог вне `XST_HOME`,
а после успешной установки удалите исходную лишнюю копию:

```sh
install -d -m 700 "$HOME/.local/share/xst-import"
chmod 600 "$HOME/.local/share/xst-import/provider-source.json"
XST_SUB_FILE="$HOME/.local/share/xst-import/provider-source.json" \
  XST_ZSHRC=0 ./install.sh
```

Не коммитьте даже «временно» сохранённый ответ. Если нужен тестовый fixture,
удалите все реальные endpoint, UUID, ключи, SNI, домены и remarks.

## Диагностика

Нормализацию можно проверить без установки:

```sh
python3 lib/xstlib.py normalize \
  "$HOME/.local/share/xst-import/provider-source.json" \
  "$HOME/.local/share/xst-import/normalized.json"
chmod 600 "$HOME/.local/share/xst-import/normalized.json"
```

Затем проверьте каждый выбранный полный конфиг тем же бинарником xray-core,
который будет использовать выбранный launchd scope. Не вставляйте содержимое конфигов в
отчёт; достаточно exit code и версии бинарника.
